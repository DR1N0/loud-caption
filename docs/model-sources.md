# Offline sherpa-onnx model sources

The app uses two sherpa-onnx model files — a SenseVoice ASR model and a Silero VAD model. They are **not** bundled in the APK; instead, `lib/speech/sense_voice_model_download.dart` downloads, checksum-verifies, and installs them into app-private storage the first time the app runs, blocking on a dedicated download screen until that completes. This keeps the installable APK small (previously ~198MB with both models bundled) at the cost of requiring a network connection on first launch.

Authoritative source for both files: the `asr-models` release of <https://github.com/k2-fsa/sherpa-onnx>. GitHub is unreliable from some regions (mainland China in particular), so each file also has two GitHub-release-proxy mirrors as fallbacks — `ghfast.top` and `gh-proxy.com`, both verified (matching `Content-Length`) to serve the identical release asset, not a re-packaged copy — tried in order after the primary. `lib/speech/sense_voice_model_download.dart` has the exact URLs.

The SenseVoice row has two meaningfully different sizes: the `.tar.bz2` archive is compressed (~164 MB), but only `model.int8.onnx` and `tokens.txt` are extracted from it and installed — those extracted files are larger on disk (~240 MB combined) because the archive is bzip2-compressed.

## Download, verification, and installation

`lib/downloads/model_downloader.dart` streams each file to a sibling `.part` file while incrementally computing its SHA-256, then atomically renames it into place only once the digest matches the pinned value above — an interrupted or corrupted download never leaves a partial or bad file at the final path, and a relaunch simply restarts cleanly. `lib/speech/sense_voice_model_download.dart` orchestrates the SenseVoice-specific steps: download the `.tar.bz2` archive to scratch storage, verify it, extract (via `package:archive`, off the UI isolate) the two files actually needed, discard the archive, then download and verify Silero VAD directly to its final destination (no extraction needed — it's already a single file).

Because the installed files are the same flat `model.int8.onnx`/`tokens.txt`/`silero_vad.onnx` either way, on-device storage footprint is unchanged from the old bundled-asset approach: approximately 240 MB (SenseVoice) + 0.6 MB (Silero VAD) ≈ 240 MB, now paid at first launch instead of at install time.

`isSenseVoiceModelReady()` checks only that these files exist at their fixed destination paths — it does not re-verify their SHA-256 on every app launch, since the only way a file can land at that path is via the atomic verify-then-rename sequence above.

## Hy-MT2 translation model

| Component | Archive / file | Download size | Pinned SHA-256 | License |
| --- | --- | --- | --- | --- |
| Hy-MT2-1.8B (Q4_K_M) | [`Hy-MT2-1.8B-Q4_K_M.gguf`](https://huggingface.co/tencent/Hy-MT2-1.8B-GGUF/resolve/main/Hy-MT2-1.8B-Q4_K_M.gguf) | 1,133,080,448 bytes (~1.05 GiB / ~1.08 GB) | `dc5f44fcf1fa496ee7ad725982c0c8c553a4de00259b53af84c4b89fb0c06699` | Apache License 2.0 |

Authoritative source: the `tencent/Hy-MT2-1.8B-GGUF` repository on Hugging Face. Downloaded on demand by `lib/translation/hy_mt2_model_download.dart` (reusing `lib/downloads/model_downloader.dart`'s same streaming-hash-then-atomic-rename pipeline as the ASR models above) the first time the user switches into a translation mode — not at first launch, since most users may never use translation.

Hugging Face is likewise unreliable from mainland China — confirmed on-device, where hitting it first cost roughly 10 seconds before falling through — so ModelScope (`Tencent-Hunyuan/Hy-MT2-1.8B-GGUF`, Tencent's own official publish of this exact repository, hosted in mainland China) is tried first, then `hf-mirror.com` (a dedicated HF mirror), with Hugging Face itself last. All three verified as byte-identical: matching file size, and for ModelScope, the pinned SHA-256 above confirmed directly via its API.

**Why Q4_K_M and not the smaller 1.25-bit/2-bit variants.** Tencent also publishes `Hy-MT2-1.8B-1.25bit-GGUF` (~440 MB) and `Hy-MT2-1.8B-2bit-GGUF` (~573 MB), both using a custom AngelSlim "Sherry"/STQ1_0 ternary quantization. That ggml kernel is not in mainline llama.cpp — it's still an open, unmerged pull request ([ggml-org/llama.cpp#22836](https://github.com/ggml-org/llama.cpp/pull/22836)) — so no existing Flutter llama.cpp plugin can load those files. Q4_K_M is a standard ggml quantization type any such plugin's vendored llama.cpp already supports, at the cost of a larger download.

**Inference.** `lib/translation/llama_translation_engine.dart` runs the model via the `llama_flutter_android` package (MIT-licensed, vendors an unmodified llama.cpp build), on the CPU only (no GPU offload requested), with the plugin's thread count capped so it doesn't compete for every core with the ASR/VAD isolates. Prompts are hand-built to match Hy-MT2's own chat template exactly — confirmed against `train/llama_factory_support/hy_dense_template.py` in the upstream [`Tencent-Hunyuan/Hy-MT2`](https://github.com/Tencent-Hunyuan/Hy-MT2) repository, not inferred or guessed — since the model has no default system prompt and none of the plugin's built-in templates (ChatML, Llama-2, etc.) match Hunyuan's token format.

**Known upstream bug, fixed via a fork.** Real-device testing surfaced a bug in `llama_flutter_android` 0.2.6 (the latest published version at the time): its native token-streaming code (`jni_wrapper.cpp`'s `sanitizeUTF8`) validates each streamed token's raw bytes in isolation, but a single multi-byte UTF-8 character — any CJK character is 3 bytes — is routinely split across two or more consecutive BPE tokens. The plugin replaced the resulting incomplete sequence with the U+FFFD replacement character instead of buffering it to complete with the next token's bytes, so Japanese/Chinese output was garbled with scattered `�` characters (ASCII/English output was never affected, since single-byte characters can't be split). Fixed and verified on-device (dozens of Japanese generations, zero mojibake) in [dragneel2074/Llama-Flutter#2](https://github.com/dragneel2074/Llama-Flutter/pull/2); `pubspec.yaml` pins `llama_flutter_android` to the fix branch on a fork (`DR1N0/Llama-Flutter`) until that PR merges and ships in a published release, at which point the dependency should move back to a normal pub.dev version constraint.

A second real-device finding, now believed resolved without any plugin change: a native crash (`SIGABRT`, a `ggml_compute_forward_rms_norm_f32` assertion failure in llama.cpp's own CPU kernel, not the plugin's code) occurred after a few translations when a partial (uncommitted) translation's `cancel()` — which queues a `stop()` call — raced against a new `generate()` call queued immediately after for the superseding final translation; `stop()` can resolve on the Dart side before the native generation thread has fully unwound. `CaptionController` no longer triggers a translation for uncommitted partial text at all (on-device inference latency couldn't keep up with live speech anyway — see `lib/captions/caption_controller.dart`), which also removed the only caller of `TranslationRequest.cancel()` and, with it, this race — confirmed via repeated real-device translation with no further crashes.
